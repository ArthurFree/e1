我把当前 `main` 的目录结构、核心架构文档、`AppServices`、状态层、`MainArea`、IndexedDB、Desktop 能力、依赖约束以及今天最新一次 GitHub Actions 都看了一遍。

先给结论：**这个仓库的架构方向是对的，而且基础比一般个人项目扎实很多；现在最大的问题不是“架构太烂”，而是 R005 → R006 快速演进之后，系统已经进入了“复杂度收敛期”。** 继续加功能、加抽象、加阶段编号，收益会开始下降。当前最应该做的是：**先让 main 重新全绿，然后减少巨型模块、消灭临时平台逃生口、统一 Web/Desktop adapter 结构、修正文档漂移。**

### 当前架构我会这样理解

```text
                    ┌─────────────────────────────┐
                    │        React / Tiptap       │
                    │ components / editor / state │
                    └──────────────┬──────────────┘
                                   │
                              AppServices
                                   │
                    ┌──────────────▼──────────────┐
                    │         Application         │
                    │ commands / queries/services │
                    │ SaveCoordinator / Vault     │
                    └──────────────┬──────────────┘
                                   │ Ports
                    ┌──────────────▼──────────────┐
                    │            Domain           │
                    │ entities / errors / repos   │
                    │ validation / pure logic     │
                    └───────────┬─────────┬───────┘
                                │         │
                 Web Runtime    │         │    Desktop Runtime
                                │         │
           infrastructure/      │         │ platform/desktop/
           platform/web/        │         │
                │               │         │
           IndexedDB            │         │ shared/ipc
           localStorage         │         │
           BroadcastChannel     │         ▼
                │               │    Electron Preload
                │               │         │
                │               │    Electron Main
                │               │         │
                │               │     Filesystem
                │               │   Markdown / Assets
```

你现在实际上已经不是一个单纯的 React Web 项目了，而是一个 **local-first + Web/Desktop 双 Runtime + Ports & Adapters 风格的笔记系统**。Web 以 IndexedDB/Tiptap JSON 为真实数据源，而 Desktop 以 Markdown 文件为真实数据源，这是当前最重要的架构特征。

分层约束这一块做得不错。`dependency-cruiser` 明确限制 domain/application/UI/infrastructure 之间的依赖，还禁止 Electron 与 Renderer 源码直接交叉引用以及循环依赖。 当前 CI 实际跑依赖分析时扫描了 **394 个模块、1618 条依赖，未发现依赖违规**，所以现在并不是典型的“层级失控”。

而且 `AppServices` 已经收紧到 commands / queries / application services，没有把 repository 直接暴露给 React，这一步是很重要的。

### 我认为当前最值得处理的问题

1. **P0：当前 main 是红的，这应该压过所有架构重构。**

   今天最新的 `5547ed1` C5 提交，GitHub Actions 的 `quality` 和 `e2e` 两个 job 都失败；前一个 C4.1 提交也是失败状态。

   quality 失败里面其实暴露了两个不同问题。

   第一是：

   ```ts
   expect(elapsed).toBeLessThan(500)
   ```

   `perf.bench.test.ts` 自己已经注明 fake-indexeddb 和真实 IndexedDB 性能特征不同，但仍然把 500ms 的 wall-clock 时间作为普通 CI 的硬门禁。

   GitHub Runner 这次测到了约 `540ms`，于是整个质量门禁失败。

   **这个测试设计应该调整，而不应该简单把 500 改成 800。**

   我建议把性能测试拆成：

   ```text
   npm test
     → correctness tests
     → 不依赖 wall-clock

   npm run test:perf
     → 独立性能任务
     → controlled runner
     → 记录趋势 / 相对回归
     → 不和普通 unit tests 混跑
   ```

   你 Electron 那部分其实已经用了更合理的做法：性能 sanity 记录耗时，不设脆弱硬 SLA。

   第二个比性能测试更值得重视：CI 出现了未处理的 `InvalidStateError`，调用链是：

   ```text
   WorkspaceProvider
       ↓ fire-and-forget
   WorkspaceCommandService.setLastOpened
       ↓
   repository.setLastOpened
       ↓
   IndexedDB connection 已经被 teardown
       ↓
   InvalidStateError
   ```

   CI annotation 已经定位到了 `repositories.ts:239`。

   而 `WorkspaceProvider` 当前确实存在这种模式：

   ```ts
   void workspaceCommands.setLastOpened(...).then(...)
   ```

   它没有跟 Provider 生命周期绑定，也没有统一处理 rejection。

   这不只是测试问题，它说明现在代码里存在 **unowned async task**。

   我会建立一个规则：

   ```text
   React 层禁止裸：

   void promise.then(...)

   必须：
   ├── await
   ├── catch
   └── 或交给明确拥有生命周期的 task/controller
   ```

   E2E 现在还有第三个问题：AI 流程超时，Playwright 一直找不到“文本格式”工具栏里的 `AI` 按钮。这次是 23/24 个 Web E2E 通过，一个 AI 用例超时。这个不要单纯加 timeout，而应该检查编辑器 ready、AI 配置加载和 toolbar render 三者是否存在竞态。

2. **P0/P1：架构文档已经明显落后于代码。**

   这是目前非常具体的技术债。

   `README` 开头已经写：

   > IndexedDB v5

   但同一份 README 后面的架构章节又写：

   ```text
   infrastructure # IndexedDB 实现（DB v4）
   ...
   数据库当前版本 v4
   ```

   实际代码已经明确是：

   ```ts
   export const DB_VERSION = 5;
   ```

   并且有完整的 v4 → v5 secrets store + AI key migration。

   Desktop 文档漂移更加明显。

   `runtime-boundaries.md` 还说 Desktop：

   ```text
   documentPersistence: false
   C4 后再翻 true
   persistentAssetPaths C5 后再翻 true
   ```

   但当前实际代码已经：

   ```ts
   persistentAssetPaths: true,
   documentPersistence: true,
   ```

   这个以后很危险，因为 AI/开发者会根据旧架构文档继续生成新代码。

   建议把“当前事实”和“历史规划”彻底分开：

   ```text

   ├── adr/                # 为什么这么设计
   ```

   特别是 `RuntimeCapabilities`，最好直接用测试锁定文档中的 capability matrix，避免两边继续漂移。

   你之前的整改成功解决了：

   ```text

   component → IndexedDB
   ```

   ```text
       +

       +

       +
   ```

   ```ts
   const state = useReducer(...)
   ```

4. **P1：`desktopExtras` 是目前最明显的架构“逃生口”。**

   这一点代码自己其实已经承认了。

   `AppServices` 现在有：

   ```ts
   desktopExtras?: {
     rescanVault(...)
     approveSourceLossy?(...)
     approveOutputLossy?(...)
     approveIdentityAdoption?(...)
   }
   ```

   并且注释明确说：

   > 后续应演进为正式 port，不长期保留平台特例。

   我建议 **R006 验收之后第一时间干掉它**。

   因为你的核心原则是：

   ```text
   UI 不知道它运行在 Web 还是 Desktop
   UI 只知道 capability
   ```

   结果共享 `AppServices` 里面出现了一个叫：

   ```text
   desktopExtras
   ```

   本身就在破坏这套模型的语义。

   可以演化成平台无关能力：

   ```ts
   vaultMaintenance?: {
     rescan(vaultId: string): Promise<void>
   }

   documentSafety?: {
     approveLossySource(pageId: string): void
     approveLossyOutput(pageId: string): void
     approveIdentityAdoption(pageId: string): void
   }
   ```

   然后：

   ```text
   Web implementation
        ↓
   unavailable / noop / capability false

   Desktop implementation
        ↓
   real implementation
   ```

6. **P1：Web JSON / Desktop Markdown 双真相模型，是未来最大的复杂度来源。**

   这个设计不是错，甚至我认为方向很好。

   Web：

   ```text
   Tiptap JSON = canonical data
   IndexedDB = source of truth
   ```

   Desktop：

   ```text
   Markdown = canonical data
   filesystem = source of truth
   ```

   架构文档也明确规定了 DUAL-03 / DUAL-04 / DUAL-07。

   问题在于以后每新增一个编辑能力：

   ```text
   underline
   table extension
   mention
   attachment
   alignment
   custom block
   callout
   database
   ...
   ```

   都必须回答：

   ```text
   Tiptap JSON
        ↓
   Markdown
        ↓
   第三方修改
        ↓
   Markdown
        ↓
   Tiptap JSON

   是否无损？
   ```

   你现在的 lossy gate 是正确方向，但下一步千万不要让这些判断继续往 `MainArea` 堆。

   应该形成：

   ```text
   DocumentCodec
        │
        ├── parse()
        ├── serialize()
        ├── inspectCompatibility()
        └── migration/version
   ```

   然后 UI 只消费：

   ```ts
   compatibility.level
   compatibility.issues
   allowedOperations
   ```

   而不知道 `wiki-link/raw-html/local-image-width/...` 的各种具体业务规则。

### 有一点我反而不建议你改

**不要因为现在文件变多，就把 Application/Domain/AppServices 这些层删掉。**

你现在要做 Desktop，并且 Desktop Markdown 和 Web IndexedDB 是两套完全不同的 persistence model。此时：

```text
UI
 ↓
Application
 ↓
Port
 ↓
Web/Desktop Adapter
```

这套抽象实际上开始真正产生价值了。

如果项目一直只是 IndexedDB Web App，那我会认为目前有一点过度设计；但既然 Electron + filesystem + Markdown 已经真正接通，那么现在这套边界是有意义的。尤其 `ContentVersionToken`、`SaveCoordinator`、repository ports、IPC boundary、PathGuard、AtomicFileWriter 这些东西，都是双端项目真正需要的。

**所以不是“推倒重构”，而是“停止横向扩层，开始纵向收敛”。**
