# R004 架构与数据一致性整改方案

## 一、整改目标

本轮整改聚焦五个结果：

1. 修复保存协调器后半程的并发竞态，避免附件误删、恢复缓冲误清和保存状态误报。
2. 统一所有文档内容写入路径，禁止组件绕过应用服务直接写正文仓储。
3. 拆解 `AppState.tsx`，使四个状态域不仅在 Context 层分离，也在状态所有权和业务动作层分离。
4. 消除工作区加载过程中的全库扫描，提高多工作区、大数据量场景的稳定性。
5. 增加跨标签页、存储配额、CI 和架构约束，建立长期维护基线。

当前仓库虽然已经建立 `domain / application / infrastructure / state / components / editor` 分层，但 `AppServices` 仍向上层暴露仓储，部分组件直接调用正文和版本仓储；保存协调器也只在正文保存后检查一次 generation。

### 0.2 增加保存后半程竞态测试

现有测试主要门控 `content.save()`，但没有门控以下步骤：

- `revision.add()`；
- `revision.pruneInterval()`；
- `attachments.removeOrphans()`；
- `recovery.clear()`。

新增测试时序：

```text

→ 保存 A 的 content.save 完成
→ revision.add 或 removeOrphans 挂起
→ 用户继续编辑 B，generation 递增
→ 放行 A 的后处理
→ 验证：
   - 不发布 saved
   - 不清除 B 的恢复缓冲
   - 不误删 B 新增的附件
```

现有测试覆盖了正文保存期间继续编辑，但没有覆盖正文已经保存、后处理仍在执行的窗口。

### 0.3 增加空重试测试

测试：

```ts
await expect(coordinator.retryLatest()).rejects.toThrow("没有可重试的保存");
```

当前 `retryLatest()` 在没有 pending 和 lastFailed 时仍创建 waiter，但不会启动 drain，Promise 可能永远不结束。

### 0.4 增加架构扫描规则

# 四、阶段 1：修复保存协调器并发边界

## 目标

保证保存流程的每个危险副作用都受到 generation 和快照时间保护。

## 需要修改的文件

```text
src/application/services/SaveCoordinator.ts
src/application/services/SaveCoordinator.test.ts
src/domain/repositories.ts
src/infrastructure/repositories.ts
src/infrastructure/memory/repositories.ts
src/components/editor/SavePostCommitRace.test.tsx
src/components/editor/SaveAttachmentRace.test.tsx
```

## 具体任务

### 1.1 为保存快照增加时间边界

修改 `SaveSnapshot`：

```ts
export interface SaveSnapshot {
  pageId: string;
  generation: number;
  capturedAt: number;
  contentJson: unknown;
  textSnapshot: string;
}
```

在 `enqueue()` 创建快照时记录：

```ts
capturedAt: Date.now();
```

该字段用于保护快照产生后新建的附件。

### 1.2 增加统一最新性判断

```ts
private isCurrent(snapshot: SaveSnapshot): boolean {
  return (
    !this.disposed &&
    snapshot.generation === this.generation
  );
}
```

不要缓存一个长期使用的 `isLatest` 布尔值。

需要在以下节点重新调用：

```text
content.save 完成后
自动版本创建前
版本清理前
附件清理前
恢复缓冲清理前
发布 saved 前
```

### 1.3 修改附件清理接口

当前 `removeOrphans(pageId, referencedIds)` 可能把快照产生之后新增、但尚未进入新正文快照的附件删除。

改成：

```ts
removeOrphans(
  pageId: string,
  referencedIds: string[],
  options?: {
    createdBeforeOrAt?: number;
  },
): Promise<number>;
```

基础设施实现只允许删除：

```ts
!referencedIds.has(attachment.id) && attachment.createdAt <= createdBeforeOrAt;
```

这样即使新附件已经写入 IndexedDB、但编辑器还没来得及触发 `noteEdit()`，也不会被旧快照删除。

### 1.4 拆分正文提交和维护任务

建议结构：

```ts
private async runSave(snapshot: SaveSnapshot): Promise<void> {
  const savedAt = await this.commitContent(snapshot);

  this.settleWaiters(...);
  this.deps.onSaved?.(...);

  if (!this.isCurrent(snapshot)) return;

  await this.runMaintenance(snapshot);

  if (this.isCurrent(snapshot)) {
    this.publish({ status: "saved", savedAt });
  }
}
```

维护任务包括：

```text
自动版本
版本裁剪
孤儿附件清理
恢复缓冲清理
```

### 1.5 区分正文失败和维护失败

正文写入失败：

```text
状态进入 error
保留 lastFailed
允许用户重试
```

版本创建、附件清理或恢复缓冲清理失败：

```text
正文仍视为已保存
记录开发诊断
调用 onMaintenanceError
不要求用户重新保存正文
```

建议增加：

```ts
onMaintenanceError?(
  stage: "revision" | "attachment-cleanup" | "recovery-cleanup",
  error: unknown,
): void;
```

否则附件清理失败可能让用户误以为正文没有保存。

### 1.6 修复 retryLatest 空状态

```ts
if (!this.pending && !this.lastFailed) {
  return Promise.reject(new Error("没有可重试的保存"));
}
```

### 1.7 增加测试

至少覆盖：

1. `revision.add()` 挂起期间继续编辑；
2. `removeOrphans()` 挂起期间继续编辑；
3. 新附件创建时间晚于 snapshot，不得删除；
4. 维护失败不进入正文保存 error；
5. 最新 generation 最终正确发布 saved；
6. 空状态调用 retryLatest 明确拒绝。

## 验收标准

- 阶段 0 新增的失败测试全部通过。
- 旧 generation 永远不能发布 `saved`。
- 旧快照不能删除 `capturedAt` 之后创建的附件。
- 正文成功但维护失败时，刷新页面仍能看到最新正文。
- 当前保存协调器的串行和 latest-wins 语义保持不变。

## 建议 PR

```text
fix(save): protect post-commit maintenance with generations
fix(attachments): prevent old snapshots deleting new attachments
test(save): cover post-commit edit races
```

# 五、阶段 2：建立统一文档写入应用服务

## 目标

所有非编辑器实时输入的正文变更都通过一个应用服务执行。

## 新增结构

```text
src/application/services/
├── DocumentMutationService.ts
├── DocumentCommitService.ts
└── DocumentEditorController.ts

src/domain/
└── repositories.ts

src/infrastructure/
├── repositories.ts
└── memory/repositories.ts
```

## 具体设计

### 2.1 新增原子文档写仓储

建议新增：

```ts
export interface DocumentWriteRepository {
  createWithContent(input: {
    workspaceId: string;
    parentId: string | null;
    title: string;
    icon?: string | null;
    contentJson: unknown;
    textSnapshot: string;
  }): Promise<Page>;

  replaceContent(input: {
    pageId: string;
    contentJson: unknown;
    textSnapshot: string;
  }): Promise<DocumentContent>;
}
```

`createWithContent()` 必须在一个 IndexedDB 事务中完成：

```text
校验 workspace
校验 parent
计算 position
写 pages
写 contents
提交事务
```

现有 `PageRepository.create()` 会创建空正文，随后模板和 AI 流程再调用 `content.save()`，中间失败会留下空文档。

### 2.2 新增 DocumentCommitService

负责所有写入完成后的公共动作：

```ts
class DocumentCommitService {
  async replaceContent(input): Promise<void>;
  async createWithContent(input): Promise<Page>;
}
```

公共动作包括：

```text
写入数据库
同步搜索索引
发布文档变更事件
记录开发诊断
统一映射领域错误
```

### 2.3 SaveCoordinator 复用 DocumentCommitService

保存协调器不再直接依赖 `ContentRepository`，而依赖一个更窄的提交接口：

```ts
interface DocumentContentCommitter {
  commit(
    pageId: string,
    contentJson: unknown,
    textSnapshot: string,
  ): Promise<{ savedAt: number }>;
}
```

生产实现内部完成：

```text
contentRepository.save
searchIndex.updateText
```

从而保证实时编辑和外部内容替换使用同一提交语义。

### 2.4 新增 DocumentMutationService

建议接口：

```ts
class DocumentMutationService {
  createWithContent(input): Promise<Page>;

  replaceContent(input: {
    pageId: string;
    contentJson: unknown;
    textSnapshot: string;
    source: "markdown-import" | "template" | "ai-draft" | "corrupted-recovery";
  }): Promise<void>;

  restoreRevision(input): Promise<void>;
}
```

### 2.5 收紧 AppServices

当前容器直接公开七个仓储。

建议过渡为：

```ts
interface AppServices {
  commands: {
    documents: DocumentMutationService;
  };

  queries: {
    workspaceSession: WorkspaceSessionService;
    searchIndex: SearchIndexService;
  };

  factories: {
    createSaveCoordinator(...): DocumentSaveCoordinator;
    createAIProvider(...): AIProvider;
  };

  ports: {
    // 仅供 state/application 使用，不允许 components 访问
  };
}
```

可以先保留旧字段，但使用 `@deprecated` 标记，并在阶段 3 删除组件访问。

## 测试

新增：

```text
DocumentMutationService.test.ts
DocumentCommitService.test.ts
documentWriteRepository.test.ts
documentWriteRepository.memory.test.ts
```

测试场景：

- 页面和正文原子创建；
- 正文写入失败时页面不存在；
- 搜索索引同步；
- 内存与 IndexedDB 实现行为一致；
- workspace 和 parent 不合法时事务回滚；
- contentJson 校验失败时不写入。

## 验收标准

- 模板、AI、导入等业务已经有可调用的统一应用服务。
- `createWithContent()` 不会留下只有页面、没有正确正文的中间状态。
- IndexedDB 和内存实现通过同一契约测试。
- 保存协调器和外部写入共享正文提交能力。

## 建议 PR

```text
feat(application): add document commit and mutation services
feat(storage): support atomic document creation with content
refactor(save): delegate content commits to shared service
```

# 六、阶段 3：迁移全部直接写入流程

## 目标

删除生产组件对正文、版本和附件写仓储的直接调用。

### 3.1 模板创建

当前流程：

```text

openDocument
```

改成：

```text

openDocument
```

涉及：

```text
src/components/TemplateCenter.tsx
```

### 3.2 AI 草稿创建

涉及：


```ts
const page = await services.commands.documents.createWithContent({
```

AI 输出仍必须先经过预览和 Markdown 白名单转换。

### 3.3 Markdown 导入

当前 `createPage()` 会立即进入新文档，然后才异步覆盖正文，存在空正文加载与后续写入竞争。

改造为：

```text

documents.createWithContent
打开文档
```

涉及：

```text
src/components/PageTreeSidebar.tsx
```

### 3.4 损坏正文清空和修复

涉及：

```text
src/components/MainArea.tsx
```

以下操作改用应用服务：

```text
创建空白副本
修复后覆盖正文
应用恢复缓冲
```

并保证：

- 搜索索引同步；
- 保存状态更新；
- 恢复缓冲正确清除；
- 不直接绕过协调器。

### 3.5 安全重构版本恢复

这是本阶段风险最高的部分。

新增编辑器控制器：

```ts
interface DocumentEditorController {
  getSnapshot(): {
    contentJson: unknown;
    textSnapshot: string;
  };

  flush(): Promise<void>;

  restore(input: { contentJson: unknown; textSnapshot: string }): Promise<void>;
}
```

恢复流程：

```text
1. 校验目标版本
2. flush 当前防抖保存和协调器队列
3. 获取当前编辑器快照
4. 创建 before-restore 版本
5. 通过协调器提交目标版本
6. 更新编辑器内容但不重复产生第二次保存
7. 更新搜索索引
8. 关闭版本面板
```

不要再使用：

```text
editor.setContent
contentRepository.save
```

两条独立写入路径。

当前版本恢复先修改编辑器，再直接写正文，仍可能受到原有防抖保存影响。

### 3.6 强制架构规则

将阶段 0 的扫描改为强制失败：

```text
components/** 禁止访问 services.content
components/** 禁止访问 services.revision 的写方法
components/** 禁止访问 services.attachment 的写方法
```

建议最终做到：

```bash
grep -R "services\.content\.save" src/components
# 无结果
```

## 测试

每条迁移路径至少增加：

- 成功场景；
- 写入失败不产生半成品；
- 搜索可以立即命中新内容；
- 刷新页面后内容存在；
- 当前工作区页面镜像同步；
- 版本恢复不被旧保存覆盖。

新增关键 E2E：

```text
导入 Markdown → 立即搜索正文
模板创建 → 立即搜索正文
AI 创建 → 立即搜索正文
恢复版本 → 刷新后仍是恢复版本
```

## 验收标准

- `src/components/**` 中不存在直接正文写入。
- 所有文档创建均为页面和正文原子创建。
- 所有正文变更均同步搜索索引。
- 版本恢复不会出现恢复成功后又跳回旧内容。
- 所有架构扫描通过。

## 建议 PR 拆分

```text

refactor(import): route markdown imports through document service
refactor(ai): create AI drafts through document service
```

- 修改主题不会重渲染页面树主体。
- 重命名页面不会重渲染设置面板。
- Overlay 更新不重渲染主区编辑器。
- 工作区切换竞态测试继续通过。

## 建议 PR

```text
refactor(state): extract workspace provider
refactor(state): extract preferences and navigation providers
refactor(components): remove production useApp consumers
chore(state): retire AppState compatibility facade
```

# 八、阶段 5：IndexedDB v4 与工作区查询优化

## 目标

工作区切换时不再读取全部正文和全部页面标签关联。

当前 `WorkspaceSessionService` 调用 `content.listAll()` 后按页面 ID 内存过滤。

## 数据模型调整

### DocumentContent

```ts
interface DocumentContent {
  pageId: string;
  workspaceId: string;
  contentJson: unknown;
  textSnapshot: string;
  updatedAt: number;
}
```

新增索引：

```text
contents.workspaceId
contents.workspaceId_updatedAt
```

### PageTag

```ts
interface PageTag {
  pageId: string;
  tagId: string;
  workspaceId: string;
}
```

新增索引：

```text
pageTags.workspaceId
```

## DB v4 迁移

在 upgrade 事务中：

```text
1. 遍历 pages，建立 pageId → workspaceId 映射
2. 遍历 contents，补 workspaceId
3. 遍历 pageTags，补 workspaceId
4. 创建新索引
5. 记录无法找到页面的孤立记录数量
```

不要在迁移过程中静默猜测错误 workspace。

## 仓储接口修改

```ts
ContentRepository.listByWorkspace(workspaceId);
TagRepository.listWorkspacePageTags(workspaceId);
```

`WorkspaceSessionService.load()` 改成：

```ts
Promise.all([
  pages.listByWorkspace(workspaceId),
  tags.listByWorkspace(workspaceId),
  tags.listWorkspacePageTags(workspaceId),
  content.listByWorkspace(workspaceId),
]);
```

## 测试

迁移路径：

```text
v1 → v4
v2 → v4
v3 → v4
空数据库 → v4
包含孤立正文记录的 v3 → v4
```

性能场景：

```text
100 个工作区
每个工作区 1,000 个页面
只切换其中一个工作区
验证只读取目标工作区正文
```

当前性能基准集中在单工作区，无法反映跨工作区全表扫描成本。

## 验收标准

- 工作区会话加载不再调用 `content.listAll()`。
- 页面标签关联不再调用 `db.getAll(STORE_PAGE_TAGS)`。
- v1、v2、v3 用户数据均能升级。
- 多工作区基准中，切换成本主要与目标工作区规模相关。
- 数据迁移失败时事务整体回滚。

## 建议 PR

```text
feat(db): add workspace indexes in schema v4
refactor(session): remove cross-workspace content scans
test(db): cover v1-v4 migration paths
```

# 九、阶段 6：图片、版本和存储配额治理

## 目标

避免 Base64 图片随版本快照被重复存储，导致 IndexedDB 快速膨胀。

当前编辑器允许 Base64 图片，同时自动版本保留最多 100 份完整正文 JSON。

## 6.1 禁止新增 Base64 图片

把图片写入方式改为：

```text
File
→ AttachmentRepository.add
→ 文档节点只保存 attachmentId
→ 渲染时创建临时 Object URL
→ 节点销毁时 revoke URL
```

新增自定义扩展：

```text
src/editor/localImage.ts
```

节点属性：

```ts
{
  attachmentId: string;
  alt?: string;
  width?: number;
}
```

旧 Base64 图片继续兼容读取，但编辑器不再生成新的 Base64。

## 6.2 增加附件类型和体积校验

统一校验：

```text
单附件最大值
单文档附件总量
图片 MIME 白名单
文件名长度
Blob 实际大小
```

校验应位于 application/domain 层，不只依赖 `<input accept>`。

## 6.3 增加存储配额检测

新增：

```text
StorageQuotaService
```

功能：

```text
读取浏览器存储估算
在设置页显示已使用空间
达到阈值时提示
捕获 QuotaExceededError
提供导出数据入口
```

保存错误需要区分：

```text
普通 IndexedDB 写入失败
浏览器存储空间不足
数据库连接终止
```

## 6.4 版本历史增加空间限制

在现有数量限制之外增加总字节限制：

```text
自动版本：
- 最多 100 条
- 同时受单文档自动版本总字节预算约束

manual / before-restore：
- 默认不自动删除
- 但设置页展示占用空间
```

版本大小可用序列化后的 UTF-8 大小近似计算。

## 6.5 可选后续：内容寻址快照

若版本空间仍然偏大，再新增：

```text
contentSnapshots store
key = content hash
revision 保存 snapshotId
相同 JSON 只存一份
```

这一步复杂度较高，不与图片附件化放在同一个 PR。

## 测试

- 新增图片不会在 JSON 中出现 Base64；
- 删除图片后安全清理 Blob；
- 旧 Base64 文档仍可打开；
- 配额错误显示明确提示；
- 大文档版本裁剪符合数量和空间限制；
- 恢复版本后附件引用仍然有效。

## 验收标准

- 新写入文档不包含 Base64 图片。
- 插入大图片不会导致版本 JSON 成倍膨胀。
- 存储不足不会只显示笼统的“保存失败”。
- 用户能看到本地存储使用情况。
- 版本裁剪有可测试的确定性规则。

# 十、阶段 7：多标签页一致性和工程门禁

## 目标

处理多个浏览器标签页同时运行、数据库升级和持续集成问题。

## 7.1 IndexedDB 连接生命周期

在 `openDB()` 中增加处理：

```text
blocked
blocking
terminated
versionchange
```

行为：

- 当前标签页阻塞升级时提示用户关闭旧标签页；
- 发现其他标签页升级时关闭当前连接；
- 连接异常终止后清空缓存的 dbPromise；
- 下次操作重新连接；
- UI 显示可恢复错误，不直接白屏。

## 7.2 BroadcastChannel 同步

定义事件：

```ts
type AppSyncEvent =
  | { type: "workspace-changed"; workspaceId: string }
  | { type: "page-changed"; workspaceId: string; pageId: string }
  | { type: "content-saved"; pageId: string; version: number }
  | { type: "preferences-changed" };
```

接收后：

```text
非当前编辑文档：增量刷新
当前编辑文档且本地无修改：自动刷新
当前编辑文档且本地 dirty：显示冲突提示
```

## 7.3 正文乐观并发控制

给正文增加：

```ts
version: number;
```

保存接口：

```ts
save(
  pageId,
  contentJson,
  textSnapshot,
  expectedVersion,
): Promise<{ version: number; updatedAt: number }>;
```

事务内：

```text
读取当前 version
若不等于 expectedVersion，抛 DOCUMENT_CONFLICT
否则 version + 1 并写入
```

冲突 UI 至少提供：

```text
重新载入磁盘版本
保留当前内容并另存副本
强制覆盖
复制当前内容
```

## 7.4 增加工程脚本

`package.json`：

```json
{
  "scripts": {
    "lint": "eslint .",
    "format:check": "prettier --check .",
    "deps:check": "dependency-cruiser src",
    "test:coverage": "vitest run --coverage",
    "ci": "npm run typecheck && npm run lint && npm run deps:check && npm test && npm run build"
  }
}
```

当前脚本包含类型检查、测试和构建，但没有统一的 lint、依赖检查及 CI 入口。

## 7.5 强化架构规则

现有规则通过逐行正则扫描 import，无法识别循环依赖和语义越层。

新增规则：

```text
domain 不依赖 application/editor/state/components/infrastructure
application 不依赖 components/state/infrastructure
components 不直接访问仓储写接口
infrastructure 只能在装配根被 UI 入口引用
禁止循环依赖
禁止跨层深层路径绕过公开入口
```

## 7.6 增加 GitHub Actions

建议拆为两个 Job：

```text
quality:
  npm ci
  npm run ci
  npm run test:coverage

e2e:
  安装 Chromium
  npm run test:e2e
  失败时上传截图和 trace
```

视觉截图变化必须人工审查，不能在 CI 中自动更新基线。

## 验收标准

- 两个标签页编辑同一文档不会静默覆盖。
- 数据库升级阻塞有明确提示。
- `npm run ci` 成为本地和 PR 的统一门禁。
- 循环依赖和分层违规会阻止合并。
- E2E 失败可下载截图或 trace 定位。
