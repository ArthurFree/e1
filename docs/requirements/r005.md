# R005：Web 优先与 Electron 双端准备方案

## 一、当前仓库重新评估

### 1. 已经具备的良好基础

当前仓库已经具备双端改造需要的部分基础：

- React、Tiptap、状态组件与 IndexedDB 基础设施已分层；
- UI 不直接导入 `infrastructure`；
- `AppServices` 已经成为依赖注入入口；
- 正文写入统一经过 `DocumentCommitService`；
- 保存协调器支持串行保存、generation、恢复缓冲和乐观锁；
- 页面与正文支持原子创建；
- AppState 已经拆分成四个 Provider；
- 图片正文节点只保存 `attachmentId`，不再产生 Base64；
- ESLint、Prettier、dependency-cruiser 和 CI 已配置。

因此，项目不需要重新设计 UI，也不需要推倒现有应用层。

---

### 2. 目前还不是真正的双端架构

当前仍然是明确的单 Web 运行时：

```text
src/main.tsx
    └── createBrowserAppServices()
            ├── IndexedDB
            ├── localStorage
            ├── BroadcastChannel
            └── 浏览器 Storage API
```

入口直接装配 `createBrowserAppServices()`，还没有独立的 Web/Desktop Bootstrap。

`package.json` 也只有 Vite Web 开发、构建和测试脚本，没有 Electron 入口、主进程、preload 或桌面构建配置。

---

### 3. 当前最主要的双端阻碍

#### 3.1 AppServices 仍暴露原始仓储

当前 `AppServices` 直接暴露：

```text
workspace
page
content
revision
attachment
tag
preferences
documentWrite
```

这意味着状态层仍然知道底层仓储模型。

例如 `WorkspaceProvider` 仍然直接使用：

```text
WorkspaceRepository
PageRepository
ContentRepository
TagRepository
```

并在 React Provider 内编排创建、重命名、移动、删除、搜索索引更新和跨标签页广播。

这虽然已经比组件直写好很多，但将来接入桌面文件时，Provider 很容易出现：

```ts
if (desktop) {
  // 写 Markdown
} else {
  // 写 IndexedDB
}
```

因此还需要把业务编排进一步下沉到 application 层。

---

#### 3.2 搜索服务仍是 Web 内存实现

`DocumentCommitService` 依赖具体的 `SearchIndexService` 类，而不是搜索接口。

当前搜索索引采用工作区内存 Map：

```text
IndexedDB 内容
→ WorkspaceSessionService 全量读取工作区 contents
→ SearchIndexService.build()
→ 内存查询
```

`WorkspaceSessionData` 仍包含工作区所有正文，主要用于构建搜索索引。

Web 下这样可行，但 Electron 下不应该每次打开 Vault 都读取全部 Markdown 正文；桌面端最终应该由 SQLite 索引提供搜索。

---

#### 3.3 Markdown 转换还不是持久化级 Codec

当前 Markdown 能力是一个模块级 Tiptap Headless Editor，提供：

```ts
markdownToJson();
jsonToMarkdown();
jsonToText();
```

它适合当前的导入导出，但还没有处理：

- Frontmatter 保留；
- 稳定笔记 ID；
- 未支持语法保护；
- 相对链接解析；
- Wiki Link；
- 附件路径重写；
- 图片和附件导出；
- 换行和编码策略；
- 无损回写检测。

更关键的是，当前 `localImage` 明确不会被序列化到 Markdown，避免输出无法恢复的 `attachment:id`。这意味着现有 Markdown 导出不是完整可迁移备份。

---

#### 3.4 附件接口仍然是浏览器模型

当前领域实体直接包含：

```ts
blob: Blob;
```

附件仓储也以 `Blob` 作为主要二进制载体。

编辑器附件逻辑还直接使用：

```text
window.alert
<input type="file">
URL.createObjectURL
<a download>
```

这些属于浏览器 UI 和浏览器二进制访问方式。

Electron Renderer 虽然也有 DOM，但桌面附件最终更适合由主进程管理文件路径、自定义协议和原生文件选择。

---

#### 3.5 恢复、同步和设置仍是浏览器实现

当前恢复缓冲直接同步写入 `localStorage`。

浏览器装配根还直接创建：

- IndexedDB 仓储；
- BroadcastChannel；
- StorageConnectionEventBus；
- localStorage 恢复函数；
- OpenAI Provider。

这些能力需要抽象，但不需要现在就替换。

---

# 二、整体实施策略

## 核心原则

接下来应采用：

```text
Web 继续作为唯一正式交付端
+
所有新底层能力按双运行时设计
+
完成架构准备后再做 Electron 技术验证
```

阶段分界：

```text
阶段 0～8：Web 正式版本持续迭代
阶段 9：Electron 技术验证版
阶段 10：根据验证结果决定是否正式产品化
```

在阶段 9 之前，不加入 SQLite，不引入文件监听，不投入安装器、签名和自动更新。

# 四、数据存储目标

| 数据           | Web 正式版              | Electron 正式版              |   是否迁移 |
| -------------- | ----------------------- | ---------------------------- | ---------: |
| 笔记正文       | IndexedDB Tiptap JSON   | 本地 Markdown                |         是 |
| 笔记 ID        | IndexedDB Page ID       | Frontmatter ID               |         是 |
| 页面树         | Page 表                 | 文件夹和 Markdown 路径       |         是 |
| 标签           | Tag/PageTag 表          | Frontmatter                  |         是 |
| 图片和附件     | IndexedDB Blob          | `assets/` 真实文件           |         是 |
| 搜索索引       | 内存索引                | SQLite FTS                   | 否，可重建 |
| 版本历史       | IndexedDB               | 本机应用数据或 `.e1/history` |       可选 |
| 恢复缓冲       | localStorage            | Electron userData            |         否 |
| 主题和窗口状态 | IndexedDB               | Electron userData            |         否 |
| AI 密钥        | SecretStore 的 Web 实现 | 系统安全存储                 |         否 |
| 最近访问       | IndexedDB               | 本机应用数据库               | 通常不迁移 |

Web 继续以 Tiptap JSON 为唯一编辑真相；Electron 以后以 Markdown 文件为唯一持久化真相。两个运行时共享应用模型，但不强求物理存储一致。

# 六、阶段 1：将业务编排移出 React Provider

## 目标

让 React Provider 只负责状态生命周期，不再负责持久化业务编排。

## 新增应用服务

```text
src/application/commands/
├── WorkspaceCommandService.ts
├── PageCommandService.ts
├── DocumentCommandService.ts
├── TagCommandService.ts
└── TrashCommandService.ts

src/application/queries/
├── WorkspaceQueryService.ts
├── DocumentQueryService.ts
├── ActivityQueryService.ts
└── SearchQueryService.ts
```

## 改造 AppServices

从：

```ts
interface AppServices {
  workspace: WorkspaceRepository;
  page: PageRepository;
  content: ContentRepository;
  // ...
}
```

逐步改成：

```ts
interface AppServices {
  commands: {
    workspace: WorkspaceCommandService;
    page: PageCommandService;
    document: DocumentCommandService;
    tag: TagCommandService;
    trash: TrashCommandService;
  };

  queries: {
    workspace: WorkspaceQueryService;
    document: DocumentQueryService;
    activity: ActivityQueryService;
    search: SearchQueryService;
  };

  runtime: RuntimeServices;
}
```

原始仓储只存在于装配根内部，不再通过公开容器传给 React。

## WorkspaceProvider 的处理

当前这些逻辑移到应用服务：

- 创建知识库；
- 创建页面；
- 原子创建带正文的文档；
- 重命名；
- 收藏；
- 删除和恢复；
- 清空回收站；
- 移动页面；
- 标签修改；
- 搜索索引更新；
- 同步事件广播。

Provider 保留：

- `useReducer`；
- requestId 过期响应保护；
- 更新 Context 状态；
- 调用导航桥；
- 展示错误状态。

## 架构门禁

新增规则：

```text
src/components/** 不得 import domain/repositories
src/state/** 不得 import domain/repositories
src/components/** 不得访问 AppServices 原始 port
src/state/** 不得访问 AppServices 原始 port
```

## Web 收益

- Provider 更小；
- 业务操作可以单独测试；
- 创建、移动、删除等流程不再与 React 生命周期绑定；
- 后续 Web 功能开发更稳定。

## 双端收益

Electron 只需为命令和查询提供另一组底层实现，React Provider 不需要修改。

## 验收标准

- `WorkspaceProvider` 不再解构 repository；
- 所有页面写操作经过 application command；
- 当前 Context 对组件暴露的接口可以保持不变；
- Browser 和 Memory 实现通过相同命令测试。

# 八、阶段 3：将版本号和文档快照改成平台无关模型

## 目标

消除当前 `number version` 对 IndexedDB 自增模型的假设。

当前正文版本固定为数字，每次 IndexedDB 保存执行 `version + 1`。

Desktop 外部文件修改更适合使用内容 hash 或文件 ETag，因此应用层应使用不透明 token。

## 新模型

```ts
export type ContentVersionToken = string;

export interface DocumentSnapshot {
  documentId: string;
  workspaceId: string;
  editorDocument: unknown;
  textSnapshot: string;
  versionToken: ContentVersionToken;
  updatedAt: number;
}
```

Web 映射：

```text
IndexedDB version 5
→ versionToken "idb:5"
```

Desktop 映射：

```text
文件 SHA-256
→ versionToken "sha256:abc..."
```

## SaveCoordinator 调整

从：

```ts
expectedVersion: number;
```

改成：

```ts
expectedVersion: ContentVersionToken;
```

应用层不解析 token，只原样传递给仓储。

## 降低 Web 迁移风险

IndexedDB 内部仍可继续保存数字：

```text
持久化 DTO：number
领域模型：string token
```

由 Web Repository 完成转换，因此这一阶段不一定需要升级 DB v5。

## 验收标准

- Application 和 SaveCoordinator 不再假设版本是数字；
- Web 乐观锁语义不变；
- 现有冲突面板测试全部继续通过；
- Memory Repository 支持任意 token。

# 九、阶段 4：建设持久化级 MarkdownCodec

## 目标

把当前“导入导出工具”升级为 Web 和 Desktop 共用的文件格式核心。

## 新接口

```ts
export interface MarkdownCodec {
  parse(input: {
    markdown: string;
    relativePath?: string;
  }): Promise<ParsedNote>;

  serialize(input: {
    document: unknown;
    metadata: PortableNoteMetadata;
    assetResolver: MarkdownAssetResolver;
    mode: "portable" | "plain";
  }): Promise<MarkdownSerializationResult>;
}
```

## ParsedNote

```ts
interface ParsedNote {
  document: unknown;
  metadata: {
    id?: string;
    title?: string;
    tags: string[];
    createdAt?: string;
    updatedAt?: string;
    aliases: string[];
  };
  links: ParsedLink[];
  assets: ParsedAssetReference[];
  unsupported: UnsupportedMarkdownFeature[];
  lineEnding: "lf" | "crlf";
}
```

## 必须处理的能力

### Frontmatter

至少支持：

```yaml
---
id: 01J...
title: React Fiber
tags:
  - React
created: 2026-07-28T10:00:00+08:00
updated: 2026-07-28T11:00:00+08:00
---
```

### 链接

读取支持：

```text
[标题](../目录/标题.md)
[[标题]]
[[标题#段落]]
```

默认写入标准相对 Markdown Link。

### 附件和图片

Portable 模式下：

```markdown
![图片](../assets/image.png)
[附件](../assets/design.pdf)
```

不能继续丢弃 `localImage`。

### 不支持语法

遇到无法安全转换的内容时返回：

```ts
{
  lossy: true,
  unsupported: [...]
}
```

用户必须明确确认后才能覆盖原 Markdown。

## 测试目录

```text
fixtures/markdown/
├── frontmatter.md
├── headings.md
├── nested-lists.md
├── tables.md
├── task-list.md
├── code-block.md
├── mathematics.md
├── markdown-links.md
├── wiki-links.md
├── images.md
├── attachments.md
├── raw-html.md
└── unsupported-syntax.md
```

## 测试类型

- parse fixture；
- serialize fixture；
- parse → serialize → parse 语义等价；
- Frontmatter 未知字段保留；
- CRLF/LF 策略；
- 图片和附件路径；
- 不支持语法不会被静默删除。

## Web 收益

- Markdown 导出真正包含图片和附件；
- 导入行为更可靠；
- 为备份和迁移提供稳定格式；
- 当前 Web 用户立即受益。

## 验收标准

- Markdown 导出不再丢失图片；
- Frontmatter 可以往返；
- 每个编辑器节点都有兼容性说明；
- 不支持语法不会静默覆盖。

# 十、阶段 5：抽象附件与资源访问

## 目标

保留 Web 的 IndexedDB Blob 实现，但将浏览器专属行为从编辑器节点中移出。

## 拆分领域模型

```ts
interface AssetMetadata {
  id: string;
  documentId: string;
  name: string;
  mimeType: string;
  size: number;
  createdAt: number;
}

interface BinaryAsset {
  metadata: AssetMetadata;
  data: Uint8Array;
}
```

持久化实现可以继续使用 Blob，但 application/domain 不直接依赖 Blob。

## 新增接口

```ts
interface AssetCommandService {
  importAsset(input: ImportAssetInput): Promise<AssetMetadata>;
  removeAsset(assetId: string): Promise<void>;
}

interface AssetAccessService {
  resolveUrl(assetId: string): Promise<string>;
  download(assetId: string): Promise<void>;
}

interface AssetPicker {
  pick(options: AssetPickOptions): Promise<PickedAsset | null>;
}
```

## Web 实现

```text
WebAssetPicker
→ <input type=file>

WebAssetStore
→ IndexedDB Blob

WebAssetUrlResolver
→ URL.createObjectURL
```

## Desktop 未来实现

```text
DesktopAssetPicker
→ Electron Main 原生对话框

DesktopAssetStore
→ Vault/assets 文件

DesktopAssetUrlResolver
→ e1-asset:// 自定义协议
```

## 编辑器改造

`localImage` 和 `attachment` NodeView 只依赖：

```text
AssetAccessService
NotificationService
```

删除编辑器内的：

```text
window.alert
document.createElement("input")
直接 Repository.add()
```

NodeView 仍可创建 DOM，但不负责选文件和持久化。

## 验收标准

- Web 插入图片和附件行为保持不变；
- 编辑器扩展不依赖 `AttachmentRepository`；
- application/domain 不暴露 Blob；
- Portable Markdown 可以把资源复制到 `assets/`。

# 十一、阶段 6：抽象搜索并解除会话对全部正文的依赖

## 目标

让 Web 继续使用内存搜索，Desktop 以后可以使用 SQLite，而不修改业务层。

## 新接口

```ts
export interface SearchIndexPort {
  prepareWorkspace(workspaceId: string): Promise<void>;

  upsertDocument(input: {
    workspaceId: string;
    pageId: string;
    title: string;
    textSnapshot: string;
    updatedAt: number;
    deletedAt: number | null;
  }): Promise<void>;

  removeDocument(workspaceId: string, pageId: string): Promise<void>;

  query(workspaceId: string, query: string): Promise<SearchResult[]>;

  rebuild(workspaceId: string): Promise<void>;
}
```

## Web 实现

将当前 `SearchIndexService` 移为：

```text
src/platform/web/search/BrowserMemorySearchIndex.ts
```

它仍然可以从 IndexedDB 批量构建，查询语义保持不变。

## WorkspaceSessionService 改造

从：

```ts
WorkspaceSessionData {
  pages;
  tags;
  pageTags;
  contents;
}
```

改成：

```ts
WorkspaceSessionData {
  pages;
  tags;
  pageTags;
}
```

搜索索引由：

```ts
await searchIndex.prepareWorkspace(workspaceId);
```

独立准备。

这样 Desktop 打开 Vault 时：

```text
页面树 → 文件扫描/SQLite 元数据
搜索 → SQLite
```

不需要为了加载侧栏而读取全部 Markdown 正文。

## DocumentCommitService 改造

依赖：

```ts
SearchIndexPort;
```

而不是具体 `SearchIndexService`。

文件保存成功后：

```text
更新真实数据源
→ 更新 SearchIndexPort
→ 索引失败仅标记待重建
```

正文保存不能因为派生索引失败而显示未保存。

## 验收标准

- WorkspaceSessionData 不再携带所有正文；
- Web 搜索结果与当前实现等价；
- 删除 Web 搜索内存索引后可以重建；
- DocumentCommitService 不依赖 Web 搜索类。

# 十二、阶段 7：实现 Web Portable Vault 导入导出

## 目标

在 Electron 开发前，先建立可靠的数据迁移通道。

## 导出格式

```text
MyNotes.e1.zip
├── manifest.json
├── vault.json
├── notes/
│   ├── 工作/
│   │   └── 项目 A.md
│   └── 学习/
│       └── React.md
├── assets/
│   ├── image.png
│   └── design.pdf
└── metadata/
    ├── tree.json
    └── page-map.json
```

## vault.json

```json
{
  "format": "e1-vault",
  "formatVersion": 1,
  "vaultId": "01J...",
  "name": "我的知识库",
  "createdAt": "2026-07-28T10:00:00+08:00",
  "assetsDirectory": "assets",
  "identityMode": "frontmatter"
}
```

## 页面转换规则

| Web 数据      | Portable Vault                 |
| ------------- | ------------------------------ |
| Workspace     | Vault 根目录                   |
| Group Page    | 文件夹                         |
| Document Page | Markdown 文件                  |
| Page ID       | Frontmatter `id`               |
| Tag           | Frontmatter `tags`             |
| LocalImage    | `assets/` 文件 + Markdown 图片 |
| Attachment    | `assets/` 文件 + Markdown 链接 |
| Position      | `metadata/tree.json`           |
| Favorite      | 可选写入 metadata              |
| Trash         | 默认不导出，可选择包含         |
| Revision      | 默认不导出，可选择包含         |

## 文件名冲突

确定性处理：

```text
项目.md
项目 (2).md
项目 (3).md
```

所有路径确定后，再统一生成链接，不能边创建文件边猜路径。

## Web 导入流程

```text
读取 manifest
→ 校验格式版本
→ 解析全部 Markdown
→ 建立 noteId/path 映射
→ 导入附件
→ 创建页面树
→ 原子创建正文
→ 建立标签关系
→ 重建搜索索引
→ 输出导入报告
```

## 导入报告

至少包含：

- 成功文档数；
- 跳过文档数；
- 文件名冲突；
- 无法识别语法；
- 缺失附件；
- 无法解析链接；
- 数据格式版本；
- 是否发生有损转换。

## Web 收益

- 用户获得真正的数据备份；
- 清理浏览器数据前可以迁移；
- 可把 Web 数据导入未来 Electron；
- 可以用普通 Markdown 软件读取导出内容。

## 验收标准

- 导出的 ZIP 包含全部图片和附件；
- 导入后页面树、标签、正文一致；
- 导出 → 清空 IndexedDB → 导入能够恢复；
- 同一输入多次导出产生确定性路径。

# 十三、阶段 8：抽象其余平台服务

## 目标

把最后的浏览器专属服务从 application 容器中移到 Web Adapter。

## 8.1 RecoveryStore

```ts
interface RecoveryStore {
  write(record: RecoveryRecord): Promise<void>;
  read(documentId: string): Promise<RecoveryRecord | null>;
  clear(documentId: string, generation: number): Promise<void>;
  discard(documentId: string): Promise<void>;
}
```

Web：

```text
localStorage
```

Desktop：

```text
userData/recovery
```

---

## 8.2 SettingsStore 与 SecretStore

当前 `AIConfig` 包含明文 `apiKey` 并作为 Preferences 一部分。

拆成：

```ts
interface ApplicationSettings {
  theme: ThemeName;
  sidebarWidth: number;
  aiEndpoint: string | null;
  aiModel: string | null;
}

interface SecretStore {
  get(name: string): Promise<string | null>;
  set(name: string, value: string): Promise<void>;
  remove(name: string): Promise<void>;
}
```

Web 第一阶段仍可以用 IndexedDB 实现 SecretStore，只是从普通偏好模型中分离。

Desktop 以后使用系统安全存储。

---

## 8.3 ChangeChannel

统一：

```ts
interface ChangeChannel {
  publish(event: ApplicationChangeEvent): void;
  subscribe(callback: ChangeCallback): () => void;
}
```

Web 实现：

```text
BroadcastChannel
```

Desktop 实现：

```text
Electron IPC + 文件监听事件
```

---

## 8.4 StorageHealthService

统一：

```ts
interface StorageHealthService {
  estimate(): Promise<StorageUsage>;
  subscribe(callback: StorageHealthCallback): () => void;
}
```

Web 实现：

```text
navigator.storage
IndexedDB connection lifecycle
```

Desktop 实现：

```text
磁盘剩余空间
SQLite 状态
Vault 可写状态
```

## 验收标准

- `browserServices.ts` 只负责装配，不含业务判断；
- application 不直接调用 localStorage、BroadcastChannel 或 StorageManager；
- Web 行为不变；
- 所有平台接口有 Memory 实现和契约测试。

# 十五、阶段 10：Electron 正式数据层

技术验证成功后再投入。

## 10.1 SQLite 派生索引

SQLite 保存：

- noteId/path/title；
- Tags；
- Headings；
- Links/backlinks；
- textSnapshot；
- FTS；
- hash；
- parserVersion；
- indexedAt。

不保存唯一正文。

## 10.2 文件监听

```text
文件系统事件
→ debounce
→ stat/hash 校验
→ 更新 SQLite
→ ChangeChannel
→ Renderer 刷新或提示冲突
```

文件监听失败时，应用重新聚焦和用户手动刷新必须能够触发重扫。

## 10.3 Desktop 回收站

推荐：

```text
Vault/.e1/trash/
```

并保存：

```text
原相对路径
删除时间
页面 ID
```

恢复时回到原路径；路径被占用时使用确定性重命名。

## 10.4 页面排序

文件系统本身没有稳定排序，应保存在：

```text
Vault/.e1/tree.json
```

Markdown 文件夹仍然可以被普通软件直接读取；E1 特有排序只是增强信息。

## 10.5 版本历史

第一版建议：

```text
Electron userData/revisions/<vaultId>
```

Portable Export 时可选择导出到：

```text
.e1/history/
```

## 10.6 Web → Desktop 迁移

直接读取阶段 7 定义的 Portable Vault，不让 Desktop 依赖 IndexedDB schema。

## 验收标准

- 删除 SQLite 后可以重建；
- 移动文件后稳定 ID 不变；
- 外部改名可以被识别；
- Web 导出可由 Desktop 打开；
- Desktop Vault 可由普通 Markdown 软件打开。

# 十六、Web 功能后续开发规则

阶段实施期间，Web 功能可以继续迭代，但每个新功能必须遵守以下规则。

## 新增编辑器节点

必须同时提供：

```text
Tiptap schema
运行时 JSON 校验
Markdown 解析
Markdown 序列化
Portable Vault 行为
未知/有损处理
```

不能只实现 Tiptap JSON。

## 新增数据实体

必须明确：

```text
Web 存在哪里
Desktop 存在哪里
是否属于可迁移用户数据
是否可以从 Markdown 重建
是否进入 Portable Vault
```

## 新增平台功能

使用 Capability：

```ts
capabilities.fileWatching;
```

不能判断平台：

```ts
isElectron;
```

## 新增存储操作

必须经过：

```text
Application Command
→ Port
→ Web/Desktop Adapter
```

不能在组件或 Provider 中直接调用 IndexedDB、localStorage 或文件系统。

## 新增搜索字段

必须通过 `SearchIndexPort`，不能只修改 Web 内存索引。

## 新增附件能力

必须通过 Asset Service，不能把 Blob 或文件路径写进共享领域模型。

# 二十、最终建议

当前不应该立刻开发完整 Electron，也不应该继续以“纯 Web、以后再改”的方式增加底层功能。

正确路线是：

```text
近期：
Web 功能继续交付
+
完成 Application/Runtime/Markdown/Asset/Search 五个边界

中期：
实现 Portable Vault
+
完成 Electron 最小技术验证

后期：
根据桌面需求决定是否投入 SQLite、文件监听和正式发布
```

其中最优先的不是 Electron Shell，而是：

```text
1. 把仓储编排移出 WorkspaceProvider
2. 拆分 Web Bootstrap
3. 建设持久化级 MarkdownCodec
4. 建立完整 Portable Vault 导入导出
```

完成这四项后，Web 端功能开发不会被拖慢，同时 Electron 改造也不会演变成第二套项目。
