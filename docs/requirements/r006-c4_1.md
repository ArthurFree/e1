# 2. 背景

R006-C4 已经完成 Desktop Markdown 的真实写入闭环。

当前核心链路为：

```text
Tiptap
   ↓
DocumentSaveCoordinator
   ↓
DocumentCommitService
   ↓
DesktopContentRepository.save
   ↓
MarkdownCodec.serialize
   ↓
note.save
   ↓
AtomicFileWriter
   ↓
真实 Markdown 文件
```

已经具备：

```text
✅ SHA256 乐观锁
✅ 同目录临时文件
✅ FileHandle.sync
✅ 替换前第二次版本检查
✅ DOCUMENT_CONFLICT
✅ Transient Vault 拒写
✅ Markdown Lossy Gate
✅ Frontmatter 保留
✅ LF / CRLF 保留
✅ UTF-8 BOM 保留
✅ Stable ID Adoption
✅ note.create
✅ exclusive create
✅ SaveCoordinator 双端复用
```

当前 `AtomicFileWriter` 已经采用：

```text
第一次 SHA 检查
→ temp 写入
→ sync
→ 第二次 SHA 检查
→ rename
```

并且失败时不会主动 truncate 原文件。

Desktop 保存也已经正式启用：

```ts
documentPersistence: true
```

因此 C4 的主要架构目标已经完成。

但在 C4 验收中发现四类需要在附件阶段之前解决的问题：

```text
1. 不同写入口的安全规则存在重复和绕过风险

2. Stable ID Adoption 后，
   path:* → stableId 可能在同一 Session 内提前切换

3. Vault Scan Cache 中的 pageId → relativePath
   可能保留已经失效的旧路径

4. note.create IPC 没有从 Main 层完全锁死：
   返回 noteId 必须真实存在于磁盘 Frontmatter
```

另外：

```text
AtomicFileWriter 第二次 SHA 冲突
```

虽然生产代码已经实现，但目前测试尚未真正制造“第一次检查后、第二次检查前发生外部修改”的场景。

本阶段必须完成这些安全边界的收口。

---

# 3. 阶段目标

R006-C4.1 不增加大型新产品功能。

目标只有一个：

> **确保 E1 Desktop 的所有 Markdown 写入路径都遵守完全相同的数据安全、身份和版本规则，并确保一次 Session 内不会因为磁盘 Stable ID 建立或重新扫描产生页面身份跳变。**

最终要求：

```text
                Shared Desktop Write Pipeline
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
ContentRepository.save       DocumentWriteRepository
              │                         │
              └────────────┬────────────┘
                           ▼
             DesktopMarkdownWriteService
                           │
                 ┌─────────┼─────────┐
                 ▼         ▼         ▼
              Identity   Lossy    Metadata
                Gate     Gate      Preserve
                 │         │         │
                 └─────────┴─────────┘
                           ↓
                    MarkdownCodec
                           ↓
                       note.save
                           ↓
                   AtomicFileWriter
```

不能再存在：

```text
保存入口 A
→ 有安全检查

保存入口 B
→ 直接 serialize + note.save
```

# 5. 核心不变量

所有 Markdown 内容写入必须经过同一个：

```text
Desktop Markdown Write Pipeline
```

不得存在绕过 Lossy / Identity / Version Gate 的写入入口。

同一个 Desktop Session 内：

```text
Page.id
```

一旦分配，不因：

```text

重新扫描
自动保存
```

发生改变。

## INV-C4.1-03

```text
磁盘 Frontmatter id
```


重新扫描后：

```text

```

必须反映磁盘当前状态。

```text
returned.noteId

disk frontmatter.id
```

AtomicFileWriter 的：

```text
第二次 SHA 校验
```

# 13. C4.1-B：Stable ID Session Alias

## 13.1 当前问题

对于原本没有 Frontmatter ID 的文件：

```text
React.md
```

打开时：

```text
Page.id
=
path:React.md
```

用户选择：

```text
启用编辑
```

后生成：

```text
stableNoteId
=
abc-123
```

并在第一次保存写入：

```yaml
---
id: abc-123
---
```

当前 Session 按 C4 设计仍继续使用：

```text
path:React.md
```

这是正确的。

但重新扫描后，磁盘已经拥有：

```text
id: abc-123
```

扫描器自然会生成：

```text
Page.id = abc-123
```

这样会形成：

```text
当前编辑器:
path:React.md

页面树:
abc-123
```

的身份分叉。

# 16. FR-09 当前 Session ID 保持

同一进程、同一 Vault Session 内：

```text

```

```text
stable id = abc
relativePath = React.md
```

```text

```

```text

```

而不是：

```text

```

# 17. FR-10 重启后的身份升级

Alias Registry：

```text
仅内存
```

不持久化。

因此：

```text
关闭应用
↓
重新启动
↓
重新扫描
```

此时：

```text
Page.id = abc
```

即磁盘 stable ID 正式成为新 Session 身份。

这是预期行为。

```ts
Map<
  string, // vaultId
```

```ts
private readonly pageRelativePathsByVault =
```

# 22. FR-14 Scan 使用整体替换

每次：

```text

```

```text
const nextIndex = new Map()
```

最后：

```text
pageRelativePathsByVault.set(
```

```text

```

# 23. FR-15 invalidate 同时清理路径索引

```ts
  snapshots.delete(vaultId);

```

# 34. C4.1-E：AtomicFileWriter 第二次 SHA 真并发测试

## 34.1 当前问题

生产代码已经实现第二次：

```text
rename 前 SHA 检查
```

但是现有测试中的“第二次 SHA 冲突”实际仍然在第一次检查时制造冲突。

测试注释本身也明确说明这一限制。

因此目前测试并不能证明：

```text
第一次检查通过
↓
外部修改
↓
第二次检查捕获
```

这一核心保证。

---

# 35. FR-25 可测试的 Atomic Writer Race Point

允许给 AtomicFileWriter 内部增加：

```ts
interface AtomicWriteHooks {
  afterTempSynced?(): Promise<void>;
}
```

或等价依赖注入机制。

要求：

* 不进入 IPC Contract；
* 不暴露给 Renderer；
* 生产调用不传；
* 只用于单元测试制造确定性竞态。

如果实现者认为更适合使用 FS Dependency Injection，也允许替代。

---

# 36. FR-26 真正的第二次冲突测试

测试流程必须是：

```text
磁盘 A
↓
expected = hash(A)

atomicWrite 开始
↓
第一次 SHA：
A === A
通过

↓
temp 完成 + sync

↓ test hook

外部程序：
A → B

↓
Atomic Writer 第二次读取

current = hash(B)
expected = hash(A)

↓
DOCUMENT_CONFLICT
```

最终必须满足：

```text
磁盘仍然 = B
```

且：

```text
temp 文件不存在
```

---

# 37. FR-27 第二次检查错误 Payload

必须继续包含：

```text

currentVersionToken
```

便于冲突诊断。

# 66. C4.1 成功标准

C4.1 不是为了增加用户可见功能。

成功标准是：

> **无论从哪个应用层入口修改 Desktop Markdown，都必须经过同一套安全规则；同时 Stable ID 建立、重新扫描和缓存刷新不能破坏当前编辑 Session。**

只有这一层稳定后，附件系统才适合开始复用：

```text
relativePath
Vault scope
Markdown serialization
Atomic write
Stable identity
```

这些已经验证过的基础能力。
