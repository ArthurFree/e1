# e1 项目架构整改实施规划

## 一、整改目标

本次整改不改变产品定位，继续保持：

- React + Tiptap 单页应用；
- IndexedDB 本地优先；
- 无账号、无云同步、无多人协作；
- 文档 JSON 作为正文唯一数据源；
- 用户现有数据可原地升级。

整改主要解决五类问题：

1. 编辑器保存存在并发覆盖和状态误报风险；
2. 工作区切换期间可能出现新旧数据混合；
3. UI 和状态层直接依赖 IndexedDB 实现；
4. `AppState` 职责过多，导致维护困难和无关重渲染；
5. IndexedDB 索引未充分利用，数据量增长后性能会下降。

当前仓储接口已经定义在领域层，但 `AppState`、`DocumentEditor`、`MainArea` 和部分页面组件仍直接导入具体仓储实现，因此“可替换基础设施层”的设计目标尚未真正实现。

## 阶段 1：重构编辑器保存系统

这是最高优先级阶段。

当前每次防抖结束都会直接启动异步保存，保存、附件清理、自动版本生成和保存状态更新在同一个异步函数中，但没有串行队列或内容版本判断。

### 1.1 新增 `SaveCoordinator`

新增：

```text
src/application/services/SaveCoordinator.ts
```

核心接口：

```ts
export interface SaveSnapshot {
  pageId: string;
  generation: number;
  contentJson: unknown;
  textSnapshot: string;
}

export interface SaveResult {
  generation: number;
  savedAt: number;
}

export interface SaveCoordinator {
  enqueue(snapshot: SaveSnapshot): Promise<SaveResult>;
  flush(): Promise<void>;
  retryLatest(): Promise<SaveResult>;
  hasPending(): boolean;
  dispose(): Promise<void>;
}
```

核心规则：

1. 每次编辑时 `generation + 1`；
2. 同一文档所有保存串行执行；
3. 队列中只保留最新尚未执行的快照；
4. 旧 generation 保存完成后不能把 UI 标记为 `saved`；
5. 只有最新 generation 保存成功时才执行附件清理；
6. 自动版本生成必须跟随成功保存的最新快照；
7. 保存失败后保留最新快照用于重试。

推荐内部结构：

```ts
class DocumentSaveCoordinator {
  private generation = 0;
  private savedGeneration = 0;
  private pending: SaveSnapshot | null = null;
  private running: Promise<void> | null = null;
}
```

### 1.2 拆分保存职责

将当前 `DocumentEditor.doSave` 拆为三个应用服务动作：

```text
SaveDocumentContent
CreateIntervalRevision
CleanupDocumentAttachments
```

执行顺序：

```text
保存正文
  ↓
确认该 generation 仍是最新
  ↓
生成间隔版本
  ↓
清理孤儿附件
  ↓
发布 saved 状态
```

### 1.3 修改 `DocumentEditor`

`DocumentEditor` 只负责：

- 监听 Tiptap 更新；
- 生成快照；
- 把快照提交给 coordinator；
- 展示 coordinator 状态；
- 文档切换时调用 `flush()`；
- 销毁时调用 `dispose()`。

不再直接导入：

```ts
contentRepository;
revisionRepository;
attachmentRepository;
```

当前组件同时承担编辑器装配、保存、附件清理和版本生成，应把持久化流程移出 React 组件。

### 1.4 关于 `beforeunload`

保留 `beforeunload` 监听，但不能继续声称它能够保证 IndexedDB 异步写入完成。

建议增加一个小型恢复缓冲：

```text
localStorage:
pending-document-recovery:{pageId}
```

只保存：

- pageId；
- contentJson；
- generation；
- timestamp。

正常保存成功后删除恢复缓冲。应用启动时如果发现恢复内容比 IndexedDB 新，则提示用户恢复。

附件 Blob 不写入 localStorage，附件继续依赖正常 IndexedDB 流程。

### 验收标准

- 并发保存永远按提交顺序串行执行；
- 旧保存完成不会覆盖新内容；
- 保存状态不会在仍有未保存内容时显示“已保存”；
- 快速关闭或刷新后可恢复最后一份正文快照；
- 附件不会被旧快照误删；
- 保存失败后可以重试最新内容。

### 预计工作量

3～5 人日。

## 阶段 2：工作区会话原子化

当前 `switchWorkspace` 会先更新 `workspaceId`，再分别异步加载页面和标签。加载过程中可能出现工作区已经切换，但页面和标签仍属于旧工作区的短暂状态。

### 2.1 新增会话模型

```ts
export interface WorkspaceSession {
  status: "idle" | "loading" | "ready" | "error";
  requestId: number;
  workspaceId: string | null;
  pages: Page[];
  tags: Tag[];
  pageTags: PageTag[];
  error: string | null;
}
```

### 2.2 新增 `WorkspaceSessionService`

文件：

```text
src/application/services/WorkspaceSessionService.ts
```

接口：

```ts
load(workspaceId: string): Promise<WorkspaceSessionData>;
```

内部通过一次 `Promise.all` 加载：

```ts
const [pages, tags, pageTags] = await Promise.all([
  pageRepository.listByWorkspace(workspaceId),
  tagRepository.listByWorkspace(workspaceId),
  tagRepository.listWorkspacePageTags(workspaceId),
]);
```

服务只返回数据，不直接修改 React 状态。

### 2.3 React 层采用单次提交

```ts
const requestId = ++requestIdRef.current;

dispatch({
  type: "workspace/load-start",
  workspaceId,
  requestId,
});

const result = await service.load(workspaceId);

if (requestId !== requestIdRef.current) return;

dispatch({
  type: "workspace/load-success",
  requestId,
  payload: result,
});
```

页面、标签和关联必须在同一次 reducer 更新中提交。

### 2.4 处理跨知识库打开文档

`openDocument` 应变成应用用例：

```ts
openDocument(pageId): Promise<OpenDocumentResult>
```

流程：

```text
定位页面
  ↓
确认页面存在、未删除、类型为 document
  ↓
加载所属工作区完整会话
  ↓
一次性提交工作区会话
  ↓
提交导航状态
  ↓
持久化路由
```

不允许在工作区会话未准备完成时先进入文档视图。

### 验收标准

- 快速连续切换工作区时只有最后一次请求生效；
- UI 永远不会同时看到新工作区和旧页面；
- 页面、标签、标签关联始终属于同一个工作区；
- 跨工作区打开文档不会短暂展示错误页面；
- 加载失败有明确错误状态和重试入口。

### 预计工作量

2～4 人日。

## 阶段 3：偏好与路由更新事务化

当前偏好更新采用“读取完整偏好—合并—整体写入”，多个并发更新可能相互覆盖。

### 3.1 修改仓储实现

将 `preferencesRepository.update` 改为单事务内完成：

```ts
async update(patch) {
  const db = await getDB();
  const tx = db.transaction(STORE_PREFERENCES, "readwrite");

  const stored = await tx.store.get("preferences");
  const current = normalizePreferences(stored);
  const next = {
    ...current,
    ...patch,
    id: "preferences",
  };

  await tx.store.put(next);
  await tx.done;

  return next;
}
```

### 3.2 新增 `PreferencesService`

负责串行合并以下更新：

- 主题；
- 侧栏宽度；
- AI 配置；
- 最近路由。

对于侧栏拖动，应采取：

```text
React 内存实时更新
  ↓
200～300ms 防抖持久化
```

路由更新可保留异步，但必须：

- 有统一错误捕获；
- 保证最后一次导航最终写入；
- 避免旧导航请求覆盖新导航。

### 3.3 路由状态独立

将导航状态从工作区数据状态中分离：

```ts
interface NavigationState {
  view: MainView;
  selectedPageId: string | null;
  routePersistenceStatus: "idle" | "saving" | "error";
}
```

### 验收标准

- 快速切换主题和调整侧栏宽度不会互相覆盖；
- 连续导航后刷新，总能恢复最后一个页面；
- 所有异步偏好写入错误均可观测；
- 不出现未处理的 Promise rejection。

### 预计工作量

1～2 人日。

## 阶段 4：数据校验和领域不变量

### 4.1 正文运行时校验

当前正文读取仅确认 `pageId` 存在，编辑器随后直接把 `unknown` 强制传给 Tiptap。

新增：

```text
src/domain/validation/documentContent.ts
```

需要校验：

```ts
type TiptapDocument = {
  type: "doc";
  content?: TiptapNode[];
};
```

节点必须满足：

- `type` 为字符串；
- 节点类型在允许的 schema 白名单中；
- `content` 为数组；
- `text` 仅存在于文本节点；
- 属性对象只能包含允许字段；
- 附件 ID、提及 ID、图片 src 等字段类型正确。

推荐结果类型：

```ts
type ParseResult<T> =
  { ok: true; value: T } | { ok: false; error: CorruptDataError; raw: unknown };
```

损坏数据处理：

1. 不直接把损坏数据传入编辑器；
2. 将原始数据保存至诊断记录；
3. UI 显示“文档内容损坏”；
4. 提供：

   - 尝试恢复；
   - 导出原始 JSON；
   - 创建空白副本。

### 4.2 页面关系约束

创建和移动页面时必须验证：

- 工作区存在；
- 父页面存在；
- 父页面属于同一工作区；
- 父页面未删除；
- 页面不能移动到自身或后代；
- 已删除页面不能作为正常父级；
- `kind` 合法；
- 标题长度和输入格式合法。

新增领域错误：

```ts
export type DomainErrorCode =
  | "WORKSPACE_NOT_FOUND"
  | "PAGE_NOT_FOUND"
  | "PARENT_NOT_FOUND"
  | "CROSS_WORKSPACE_PARENT"
  | "PAGE_TREE_CYCLE"
  | "PARENT_IN_TRASH"
  | "CORRUPTED_DOCUMENT";
```

不要在仓储中继续抛出只有中文字符串的普通 `Error`。应用层根据错误代码转换成用户提示。

### 4.3 标签关系约束

`setPageTags` 必须验证：

- 页面存在；
- 标签存在；
- 标签和页面属于同一工作区；
- 页面未永久删除。

### 验收标准

- 损坏正文不会导致编辑器白屏；
- 不能创建跨工作区父子关系；
- 不能给页面绑定其他工作区标签；
- 所有领域错误都有稳定错误码；
- UI 不依赖解析错误字符串判断错误类型。

### 预计工作量

3～4 人日。

## 阶段 7：IndexedDB 性能优化和 v3 迁移

当前数据库版本为 2，并已经存在部分索引，但多个查询仍通过 `getAll()` 全量读取后过滤。

### 7.1 数据库升级到 v3

```ts
export const DB_VERSION = 3;
```

新增索引建议：

```text
pages:
- workspaceId
- workspaceId_parentId
- workspaceId_deletedAt
- workspaceId_updatedAt
- workspaceId_lastOpenedAt
- workspaceId_favoriteAt

contents:
- updatedAt

tags:
- workspaceId

pageTags:
- pageId
- tagId

trash:
- deletedAt
```

注意：IndexedDB 对 `null` 索引值的行为需要通过测试确认。对于需要稳定查询的 nullable 字段，可以增加规范化字段：

```ts
isDeleted: 0 | 1;
isFavorite: 0 | 1;
```

### 7.2 改写查询

将：

```ts
db.getAll(STORE_PAGES).filter(...)
```

改为：

```ts
db.getAllFromIndex(STORE_PAGES, "workspaceId", workspaceId);
```

创建页面时，只查询同工作区、同父级兄弟。

标签查询直接使用 `workspaceId` 索引。

### 7.3 搜索优化

第一阶段不需要上复杂全文搜索引擎。

建议建立工作区级内存索引：

```ts
interface SearchIndexEntry {
  pageId: string;
  titleNormalized: string;
  textNormalized: string;
  updatedAt: number;
}
```

加载工作区时构建一次；正文保存和页面重命名时增量更新。

数据量进一步增长后，再考虑：

- 分词；
- 拼音索引；
- Web Worker；
- MiniSearch 或自有倒排索引。

### 7.4 页面树算法优化

`collectSubtreeIds` 当前会在循环中反复过滤整个页面数组。

改成预构建邻接表：

```ts
const childrenByParent = new Map<string | null, Page[]>();
```

复杂度由接近 `O(n²)` 降为 `O(n)`。

### 7.5 清空回收站事务化

当前清空回收站会逐个根页面调用 `purge`。

改为：

```ts
purgeWorkspaceTrash(workspaceId);
```

一次事务处理：

- pages；
- contents；
- pageTags；
- trash；
- revisions；
- attachments。

### 验收标准

建议用三组数据进行测试：

```text
小型：100 页面、100 文档
中型：2,000 页面、1,500 文档
大型：10,000 页面、8,000 文档
```

目标参考：

- 工作区切换：中型数据 < 300ms；
- 搜索响应：中型数据 < 100ms；
- 页面树拖动：中型数据无明显卡顿；
- 清空回收站为一次事务；
- v2 → v3 迁移后数据完整；
- 迁移失败不会留下半升级数据库。

### 预计工作量

3～5 人日。
