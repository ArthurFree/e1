# R006：Electron Desktop 本地 Vault 技术验证版

## 1. 背景

E1 当前以 Web 为正式运行端，使用 IndexedDB 保存页面、正文、附件、版本和偏好。

经过 R003、R004、R005 后，项目已经完成：

- 保存一致性与乐观锁；
- Application Commands / Queries；
- Web Runtime 独立装配；
- RuntimeCapabilities；
- 持久化级 MarkdownCodec；
- Asset 服务抽象；
- SearchIndexPort；
- Portable Vault 导入导出；
- RecoveryStore；
- ChangeChannel；
- SecretStore；
- StorageHealthService。

因此下一阶段不再继续做“为 Electron 准备”的抽象，而是用真实 Desktop Runtime 验证这些抽象是否成立。

当前仓库尚未包含 Electron Main、Preload、Desktop Runtime 或桌面构建脚本；`package.json` 仍以 `dev:web / build:web / test:web` 为主。

---

# 2. 产品目标

R006 要解决的问题是：

> 用户是否可以把一个普通本地 Markdown 文件夹直接作为 E1 知识库使用，并且该文件夹不依赖 E1 私有数据库也可以被其他工具正常读取？

本阶段需要证明以下产品闭环：

```text
选择本地文件夹
      ↓
识别为 E1 Vault
      ↓
扫描 Markdown
      ↓
生成笔记树
      ↓
打开笔记
      ↓
Tiptap 编辑
      ↓
写回原 Markdown
      ↓
关闭 E1
      ↓
VS Code / Typora 仍能直接读取
      ↓
重新打开 E1
      ↓
继续使用
```

---

# 3. 非目标

R006 是技术验证版，不追求完整 Electron 产品化。

本阶段明确不实现：

- SQLite FTS；
- 完整文件实时监听；
- 多窗口；
- 原生菜单体系；
- 系统托盘；
- 自动更新；
- 正式安装器；
- macOS / Windows 代码签名；
- 插件系统；
- 云同步；
- 多设备同步；
- Git 集成；
- 桌面全文搜索性能优化；
- Desktop 完整版本历史体系。

这些功能只有在 R006 证明本地 Vault 模型成立后才进入后续阶段。

# 4. 产品原则

## 4.1 Web 仍然是正式稳定端

R006 不改变现有 Web 数据模型。

Web：

```text
IndexedDB
→ Tiptap JSON 为真实数据源
```

Desktop：

```text
Markdown 文件
→ Markdown 为真实数据源
```

二者共享 Application/UI，但不要求使用相同物理存储。

---

## 4.2 Markdown 文件必须独立可用

Desktop 创建的笔记必须满足：

```text
没有 E1
没有 SQLite
没有 IndexedDB
没有 Electron
```

用户仍然可以：

- 找到 `.md` 文件；
- 使用文本编辑器打开；
- 查看附件；
- 复制整个文件夹；
- 在另一台机器继续使用。

---

## 4.3 SQLite 不参与本阶段

R006 搜索可以：

- 使用已有 SearchIndexPort 的简单 Desktop 实现；
- 或只实现标题筛选。

先验证：

```text
文件读写正确性
>
数据迁移正确性
>
性能
```

不能一开始同时解决 SQLite、文件监听、搜索和文件系统。

# 5. 用户故事

### US-01 打开已有 Markdown 文件夹

作为用户，我希望可以选择电脑上的一个文件夹作为知识库，这样我原来的 Markdown 笔记可以直接在 E1 中查看和编辑。

验收：

- 用户点击“打开本地知识库”；
- 系统显示原生目录选择窗口；
- 选择目录后扫描 `.md` 文件；
- 文件夹成为分组；
- Markdown 文件成为文档；
- 不修改原文件内容即可完成首次打开。

---

### US-02 创建新的本地知识库

作为新用户，我希望创建一个新的本地知识库，并知道自己的文件实际保存在哪里。

流程：

```text
新建本地知识库
→ 选择目录
→ 创建 vault.json
→ 创建必要目录
→ 进入空知识库
```

推荐结构：

```text
My Notes/
├── .e1/
│   └── vault.json
├── assets/
└── README.md / 用户笔记
```

不强制创建复杂内部目录。

---

### US-03 打开 Markdown 笔记

作为用户，我希望点击侧边栏笔记后，可以像 Web 版一样编辑。

流程：

```text
relativePath
→ Main 读取 Markdown
→ MarkdownCodec.parse()
→ Tiptap JSON
→ DocumentEditor
```

用户不应该感知底层格式转换。

---

### US-04 编辑并保存 Markdown

作为用户，我希望修改内容后自动保存到原 Markdown 文件。

保存流程：

```text
Tiptap 编辑
→ SaveCoordinator
→ MarkdownCodec.serialize()
→ Desktop Document Port
→ 临时文件
→ 原子替换
→ 返回新 versionToken
→ saved
```

现有：

```text
未保存
保存中
已保存
保存失败
```

交互必须保持。

---

### US-05 外部打开文件后仍然兼容

作为用户，我希望 E1 保存后的文件仍能直接通过其他 Markdown 软件打开。

验收：

E1 保存后：

```text
VS Code
Typora
Obsidian
普通文本编辑器
```

至少能够读取正文基本结构。

允许存在 E1 Frontmatter，但不能依赖私有二进制格式。

---

### US-06 重新打开最近 Vault

作为用户，我不希望每次启动都重新选择文件夹。

系统保存：

```text
vaultId
absolutePath
displayName
lastOpenedAt
```

下次启动：

```text
找到原目录
→ 自动打开
```

目录不存在时：

```text
“原知识库目录已移动或不可访问”
[重新定位]
[选择其他知识库]
```

# 6. Vault v1 产品格式

## 6.1 `.e1/vault.json`

建议：

```json
{
  "format": "e1-vault",
  "formatVersion": 1,
  "vaultId": "01K...",
  "name": "我的笔记",
  "createdAt": "2026-08-09T16:00:00+08:00",
  "assetsDirectory": "assets",
  "identityMode": "frontmatter"
}
```

它只记录 Vault 本身的信息。

不要记录：

```text
机器绝对路径
窗口大小
API Key
搜索数据库
本机状态
```

---

## 6.2 Markdown 笔记身份

建议 Desktop 笔记使用：

```yaml
---
id: 01K...
created: 2026-08-09T16:00:00+08:00
updated: 2026-08-09T16:12:00+08:00
tags:
  - React
  - 前端
---
```

正文：

```markdown
# React Fiber

Fiber 是 React 内部的工作单元。
```

其中：

```text
id
```

作为稳定身份。

文件：

```text
学习/React Fiber.md
```

只是当前位置。

# 7. 页面树映射规则

Desktop 不应把当前 Web `Page` 表完整复制一份作为真实目录结构。

基本规则：

```text
文件夹
→ Group

.md 文件
→ Document
```

例如：

```text
知识库/
├── 工作/
│   ├── 项目 A.md
│   └── 项目 B.md
└── 学习/
    └── React.md
```

映射为：

```text
工作
├── 项目 A
└── 项目 B

学习
└── React
```

# 8. 页面排序

文件系统没有 E1 当前 Page.position 这样的稳定自定义顺序。

R006 第一版建议：

> 默认按照文件名排序。

暂时不要引入 `.e1/tree.json` 自定义排序。

因此 Desktop 第一版：

```text
文件夹：名称排序
Markdown：名称排序
```

拖拽排序：

```text
暂时关闭
```

或者仅允许：

```text
拖动 → 移动文件夹
```

而不支持同目录自定义顺序。

这是一个重要产品取舍，可以大幅降低 R006 复杂度。

真正的自定义排序留到后续：

```text
.e1/tree.json
```

# 10. 重命名

当前 Web：

```text
renamePage
→ IndexedDB title
```

Desktop：

```text
修改标题
→ 默认不立即改文件名
```

R006 建议采用：

> **标题与文件名暂时解耦。**

Markdown：

```yaml
---
title: React Fiber 深入理解
---
```

文件仍然可以是：

```text
React.md
```

原因：

如果第一版把“标题修改”直接映射成文件重命名，就必须同时解决：

- 内部链接更新；
- 外部引用；
- 文件监听；
- 冲突；
- 重名；
- 大规模链接重写。

这不是 R006 核心目标。

后续再增加：

```text
“标题与文件名同步”
```

作为可选能力。

# 11. 文件删除

R006 不直接物理删除。

推荐：

```text

→ 移动至 Vault/.e1/trash/
```

例如：

```text
.e1/
└── trash/
    └── <noteId>/
        ├── note.md
        └── meta.json
```

或者第一版更简单：

```text
删除功能 Desktop 暂时禁用
```

如果要控制范围，我更推荐后者。

PoC 最重要的是：

```text

创建
编辑

```

删除/恢复可以留到下一阶段。

# 16. IPC 产品契约

Preload 暴露：

```ts
interface E1DesktopAPI {
  vault: {
    selectDirectory(): Promise<SelectedVault | null>;
    scan(vaultId: string): Promise<VaultScanResult>;
  };

  note: {
    read(input: ReadNoteInput): Promise<ReadNoteResult>;
    create(input: CreateNoteInput): Promise<CreateNoteResult>;
    save(input: SaveNoteInput): Promise<SaveNoteResult>;
  };

  asset: {
    pick(): Promise<PickedFile | null>;
    import(input: ImportAssetInput): Promise<ImportedAsset>;
    resolveUrl(assetId: string): Promise<string>;
  };
}
```

Renderer 不允许调用：

```ts
readFile("/任意路径");
writeFile("/任意路径");
deleteFile("/任意路径");
```

路径权限全部由 Main 控制。

# 17. 路径安全

所有文件接口必须遵守：

```text
vaultId
+
relativePath
```

Main：

```text
resolve Vault 根
→ normalize
→ realpath
→ 检查是否仍位于 Vault 内
```

拒绝：

```text
../../
符号链接逃逸
绝对路径注入
非法文件名
```

不能相信 Renderer 传入的路径。

# 18. 文件保存一致性

使用已有 SaveCoordinator。

Desktop Save Adapter：

```text
expectedVersionToken
      ↓
读取当前 Markdown
      ↓
计算 hash
      ↓
与 expectedVersionToken 比较
```

一致：

```text
序列化
→ temp file
→ fsync
→ atomic rename
→ 新 hash
→ 返回 versionToken
```

不一致：

```text
DOCUMENT_CONFLICT
```

复用现有冲突 UI。

Desktop token：

```text
sha256:<hash>
```

Web 继续：

```text
idb:<version>
```

# 19. 外部修改冲突

R006 不做完整文件监听。

只做：

> **保存前检测。**

场景：

```text

↓

↓
用户继续在 E1 编辑
↓
E1 尝试保存
↓
hash 与打开时不同
↓
DOCUMENT_CONFLICT
```

复用现有冲突面板：

```text

另存副本
强制覆盖
复制当前内容
```

这样已经能解决最危险的静默覆盖问题。
