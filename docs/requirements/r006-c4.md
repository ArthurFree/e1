# 2. 背景

R006-C3 已经完成 Desktop Markdown 安全阅读闭环。

当前 Desktop 已具备：

```text
Electron Shell
      ↓
Desktop Runtime
      ↓
目录授权
      ↓
Vault 打开 / Transient Preview
      ↓
Markdown 扫描
      ↓
页面树
      ↓
note.read
      ↓
SHA256 versionToken
      ↓
MarkdownCodec.parse
      ↓
Tiptap
      ↓
兼容性检测
      ↓
正常阅读 / 保护性只读
```

目前已经满足：

* Renderer 不拥有任意本地路径权限；
* Vault 打开使用 Selection Token；
* 普通 Markdown 文件夹可以仅预览；
* `note.read` 已经是真实实现；
* Markdown 文件读取受 PathGuard 保护；
* 单 Markdown 文件限制 10 MiB；
* 仅支持 UTF-8 / UTF-8 BOM；
* 磁盘原始字节生成 SHA256 versionToken；
* 无 Frontmatter ID 文档继续使用 `path:<relativePath>` 会话身份；
* Markdown 阅读不会产生隐式文件写入；
* 有损 Markdown 默认进入只读状态；
* Desktop 已经可以真实展示本地 Markdown。

但当前仍然存在以下边界：

```text
note.create
→ NOT_IMPLEMENTED

note.save
→ NOT_IMPLEMENTED

DesktopContentRepository.save
→ NOT_IMPLEMENTED

documentPersistence
→ false
```

因此 C4 的核心任务是：

> 从“安全读取本地 Markdown”推进到“安全修改本地 Markdown”。

---

# 3. 产品目标

R006-C4 要证明：

> E1 可以直接编辑用户真实的 Markdown 文件，并且在自动保存、外部修改、崩溃、格式兼容和首次身份建立等情况下，不产生静默数据覆盖和不可恢复的数据损坏。

最终完成以下产品闭环：

```text
打开 Markdown
      ↓
Tiptap 编辑
      ↓
800ms 自动保存
      ↓
MarkdownCodec.serialize
      ↓
保存前兼容性检查
      ↓
expectedVersionToken
      ↓
Main 校验磁盘 SHA256
      ↓
同目录临时文件
      ↓
flush / sync
      ↓
再次校验目标 SHA256
      ↓
原子替换
      ↓
返回新的 SHA256
      ↓
SaveCoordinator 更新版本
      ↓
显示“已保存”
```

同时支持：

```text
创建新笔记
外部修改冲突
保存失败重试
强制覆盖
Frontmatter 保留
CRLF 保留
无 ID Markdown 身份建立
```

```text
  ↓
```


# 6. 产品原则

## PR-01 Markdown 仍然是 Desktop 唯一正文真相

Desktop 不建立另一份正文数据库。

真实正文：

```text
Vault/*.md
```

应用缓存、搜索索引、Recovery 等都不得成为正文唯一数据源。

---

## PR-02 SQLite 不参与正文保存

即使未来引入 SQLite：

```text
SQLite
= 可重建派生索引
```

不得变成：

```text
Markdown + SQLite 双主存储
```

---

## PR-03 保存必须经过现有 SaveCoordinator

禁止新增：

```text
DesktopSaveCoordinator
ElectronSaveService
```

Desktop 编辑必须继续经过：

```text
DocumentEditor
→ SaveCoordinator
→ DocumentCommitService
→ ContentRepository.save
```

---

## PR-04 Main 不理解 Tiptap

Electron Main 只处理：

```text
路径
字节
文件
Hash
原子写入
```

不得依赖：

```text
Tiptap
ProseMirror
React
src/editor/*
```

Markdown 序列化继续在 Renderer/Application 完成。

---

## PR-05 Renderer 不获得任意文件写权限

所有写操作只能：

```text
vaultId + relativePath
```

或者 Main 签发的一次性 Token。

不得提供：

```text
fs.writeFile(path)
```

类型 IPC。

---

## PR-06 自动保存不能静默产生有损转换

任何：

```text
Tiptap → Markdown
```

无法完全表达的内容，都必须阻止自动保存并提示用户。

---

## PR-07 外部修改优先保护

当用户同时通过：

```text
VS Code
Typora
Obsidian
其他编辑器
```

修改文件时：

> E1 宁可报告冲突，也不能静默覆盖。

# 8. C4-A：文档级写入策略

## 8.1 当前问题

当前 Runtime Capability 已存在：

```ts
documentPersistence: boolean;
```

C3 Desktop 为：

```ts
documentPersistence: false
```

这意味着当前整个 Desktop 都不会启动真实保存。

C4 接通写能力后：

```ts
documentPersistence = true
```

但不能意味着所有打开的文档都允许保存。

因为至少存在：

```text
普通初始化 Vault
Transient Preview Vault
Lossless Markdown
Lossy Markdown
无稳定 ID Markdown
```

不同情况。

因此必须把：

```text
“运行时能不能保存”
```

与：

```text
“当前文档能不能保存”
```

分开。

# 15. FR-06 原子写入流程

完整流程：

```text
target.md
    ↓
读取目标当前 bytes
    ↓
计算 SHA256
    ↓
与 expectedVersionToken 比较
```

不一致：

```text
DOCUMENT_CONFLICT
```

一致：

```text
创建同目录 temp
↓
写入完整新内容
↓
FileHandle.sync()
↓
关闭 temp
↓
重新读取 target 当前 SHA256
```

再次不一致：

```text
DOCUMENT_CONFLICT
↓
删除 temp
```

仍一致：

```text
atomic replace
↓
重新 stat
↓
计算最终 SHA256
↓
返回结果
```

# 16. FR-07 临时文件位置

临时文件必须与目标文件处于：

```text
同一目录
```

例如：

```text
学习/
├── React.md
└── .React.md.e1-tmp-<random>
```

不能写到：

```text
/tmp
userData
其他磁盘
```

避免跨文件系统 rename 无法保证原子语义。
