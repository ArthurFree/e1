# 2. 背景

R006 前两个批次已经完成 Desktop 基础运行时与本地 Vault 扫描。

当前 Desktop 已具备：

```text
Electron Shell
       ↓
Desktop Runtime
       ↓
原生目录选择
       ↓
Vault 打开 / 初始化
       ↓
递归扫描 Markdown
       ↓
文件夹 → Group
Markdown → Document
       ↓
现有 React 页面树
```

Main 进程已经具有：

* `.e1/vault.json` 读取与初始化；
* Vault 最近访问记录；
* Markdown 文件夹递归扫描；
* Frontmatter 头部提取；
* PathGuard；
* symlink 逃逸防护；
* 文件名安全校验。

当前 `VaultFileSystem` 明确承担 Vault 元信息和扫描职责，并保证扫描本身不修改 Markdown。

Renderer 已经有 `DesktopWorkspaceRepository`、`DesktopPageRepository` 和 `DesktopTagRepository`，页面树已经来自真实本地文件；但 `DesktopContentRepository.get()` 仍然明确抛 `NOT_IMPLEMENTED`。

因此当前用户体验停留在：

```text
能看到本地 Markdown 文件
        ↓
点击文件
        ↓
不能真正读取正文
```

本阶段需要将这一链路推进为：

```text
选择 Markdown
      ↓
Main 安全读取文件
      ↓
返回 Markdown 原文 + SHA256 versionToken
      ↓
Renderer 使用已有 MarkdownCodec
      ↓
检测兼容性
      ↓
Tiptap 展示
      ↓
兼容文档正常阅读
不兼容文档进入保护性只读
```

本阶段的核心原则：

> **先证明 E1 可以安全理解用户已有 Markdown，再进入下一阶段证明 E1 可以安全修改 Markdown。**

# 3. 产品目标

## 3.1 核心目标

用户可以直接打开一个本地 Markdown 文件夹，并在 E1 中查看其中的 Markdown 正文。

对于 E1 可以安全解析的 Markdown：

```text
打开
→ 正常显示
→ 可以进入编辑器交互状态
→ 本阶段不实际写盘
```

对于可能发生有损转换的 Markdown：

```text
打开
→ 检测兼容性风险
→ 默认只读
→ 明确告诉用户风险来源
```

整个阅读过程中：

> **不得因为扫描、打开、解析或展示而修改用户任何 Markdown 文件。**

---

## 3.2 技术验证目标

本阶段同时验证 R005 架构设计中的三个核心假设：

### 假设 A

Electron Main 只负责：

```text

路径
字节
Hash
```

不依赖 Tiptap、ProseMirror 或 React。

### 假设 B

Desktop 可以直接复用现有：

```text
MarkdownCodec
DocumentQueryService
DocumentEditor
React 页面树
```

而无需建立第二套 Desktop Editor。

### 假设 C

同一套领域模型能够同时表达：

```text
Web
IndexedDB Content

Desktop
Markdown File
```

# 5. 产品原则

## PR-01 打开不等于接管

用户选择一个普通 Markdown 文件夹，不代表用户已经授权 E1 修改该目录。

必须区分：

```text
打开 / 预览
```

与：

```text
初始化 / 修改
```

---

## PR-02 阅读绝不产生隐式写入

以下行为都不得修改 Markdown：

```text
选择目录
扫描 Vault
打开文档
解析 Frontmatter
解析 Markdown
进入编辑器
兼容性检测
关闭文档
切换文档
退出应用
```

---

## PR-03 无 ID 文档仍然允许阅读

Markdown 不要求预先包含：

```yaml
id: ...
```

没有稳定 ID 时继续使用：

```text
path:<relativePath>
```

作为当前会话身份。

只有进入后续真正写操作时，才讨论是否写入稳定 ID。

---

## PR-04 不支持的 Markdown 优先保护

E1 不得采取：

> “能解析多少算多少，保存时再说。”

而应采用：

```text
无法确认无损
→ 默认只读
```

---

## PR-05 Main 不理解编辑器模型

Main 不得 import：

```text
@tiptap/*
prosemirror-*
src/editor/*
React
```

Main 返回 Markdown 字符串。

Renderer 使用共享 MarkdownCodec。

---

## PR-06 Renderer 不拥有任意文件系统权限

Renderer 不允许通过构造：

```text
/Users/xxx/...
C:\Users\...
../../...
```

直接要求 Main 打开或修改任意路径。

所有本地能力必须来源于：

```text
用户显式选择
```

或者：

```text
Main 已登记的 vaultId
```

# 7. R006-C2.1：Vault 授权边界收口

## 7.1 当前问题

当前 IPC 契约允许：

```ts
vault.open({
  absolutePath: string
})
```

Main 再检查路径是否是存在目录。

虽然正常 UI 中该值来自系统目录选择器，但 Renderer 技术上仍可以伪造任意绝对路径。

因此当前权限模型实际上是：

```text
Renderer
→ 任意 absolutePath
→ Main
→ initializeVault()
```

需要改为：

```text
用户系统选择
→ Main 创建授权
→ Renderer 只能消费授权
```

---

# 8. FR-01 目录选择授权 Token

## 8.1 目录选择

调用：

```ts
vault.selectDirectory()
```

Main 打开系统原生目录选择器。

用户取消：

```ts
null
```

用户成功选择：

```ts
interface SelectedVault {
  selectionToken: string;

  vaultId: string | null;

  displayName: string;

  initialized: boolean;
}
```

Renderer 不再依赖绝对路径作为后续授权凭证。

---

## 8.2 Selection Token

Main 内存维护：

```ts
interface PendingDirectorySelection {
  token: string;
  absolutePath: string;
  createdAt: number;
}
```

例如：

```ts
Map<string, PendingDirectorySelection>
```

Token 必须满足：

* 不可预测；
* Main 生成；
* Renderer 无法推导；
* 单次消费；
* 应用退出立即失效；
* 建议 5 分钟过期。

---

## 8.3 初始化 / 打开

新增：

```ts
vault.openSelection({
  selectionToken: string;
  initialize: boolean;
})
```

Main：

```text
收到 token
↓
验证 token
↓
查找真实 absolutePath
↓
立即消费 token
↓
readVault()
```

如果已经初始化：

```text
直接打开
```

如果未初始化且：

```text
initialize = false
```

返回 transient preview 信息。

如果：

```text
initialize = true
```

才调用：

```text
initializeVault()
```

# 19. FR-11 SHA256 Version Token

读取后计算完整 Markdown 字节 SHA-256。

格式固定：

```text
sha256:<64 lowercase hex>
```

例如：

```text
sha256:9c1185a5c5e9fc54612808977ee8f548b2258d31...
```

要求：

```text
相同字节
→ token 完全相同

任意字节变化
→ token 变化
```

Application 不解析 token。

该 token 将作为 C4：

```text
expectedVersionToken
```

的起点。

# 51. 最终阶段判断

R006-C3 的成功标准不是：

> “Electron 可以显示 Markdown。”

而是：

> **E1 可以读取任意用户已有 Markdown，在不确定能否无损处理时主动保护原文件，并且整个阅读过程不会产生任何隐式文件修改。**

只有这个前提成立，E1 才有资格在下一阶段开始修改用户的真实本地数据。
